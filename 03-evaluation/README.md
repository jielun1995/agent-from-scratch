# 03 · 评估体系

## 这一课要回答的问题

> **怎么知道 Agent 做得好不好?改了 prompt 是变好了还是变坏了?**

## 一句话核心

> 没有 Eval 的 Agent 开发,本质上是凭感觉。

## 为什么 Agent 评估比普通 LLM 难一个量级

1. **没有唯一标准答案** —— 好的回答可以有 100 种写法
2. **评估的是轨迹,不是结果** —— 中间走了弯路算成功吗?
3. **非确定性** —— 同问题跑 10 次结果可能不同
4. **成本不对称** —— 一次 eval 几块钱,不能像单测那样狂跑

## 评估的四个层次

| 层次 | 评估什么 | 何时用 |
|------|---------|--------|
| **L1 单元测试** | 工具调用、节点是否正确 | 每次代码改动 |
| **L2 轨迹评估** | 执行过程是否合理 | 架构调整时 |
| **L3 结果评估** | 最终输出是否满足目标 | 上线前 |
| **L4 生产评估** | 真实流量上的表现 | 上线后持续 |

**最关键的认知**: 新手最容易直接跳到 L3, 但应该从 L1 开始一层层加。

## LLM-as-Judge 的四个真实陷阱

1. **位置偏差** —— LLM 偏向先看到的答案
2. **长度偏差** —— LLM 偏好更长的答案
3. **自我偏好** —— GPT 当 Judge 偏好 GPT 写的,Claude 偏好 Claude 写的
4. **流畅度偏差** —— 文笔好但事实错的答案可能被打高分

**不解决这些陷阱,LLM-as-Judge 就是个昂贵的玩具。**
